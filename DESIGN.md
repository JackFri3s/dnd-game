# Game Design Document

> Working title: **dnd** (personal project, not for sale). Status: draft v0.2 — the agreed concept, before any code.

## 1. The idea in one paragraph

A digital tabletop role-playing game for a group sitting around a real table. A **Main Screen** (a tablet or TV lying in the middle of the table) shows the shared hex-grid map that everyone watches. Each **Player** uses their own phone or tablet for their character: sheet, actions, dice, inventory. The **Dungeon Master (DM)** is always a real person with their own device, and they control everything that happens. The world is **procedurally generated and open**: the party might reach a generated village with its own name and people, then decide to enter a house, a cave or any other place. That place is generated when they go in, and the DM can edit it. The rules are **5th Edition**, and the game state is **saved exactly** so a session can continue from the same moment next time.

## 2. Decisions made

| Topic | Decision |
|---|---|
| Platform | Web app: every device just opens a browser. Nothing to install. |
| Hosting | **On the internet** (option a). Players join with a room code or QR code. |
| DM | Always a human with their own device, in full control. No AI DM. |
| Rules | D&D 5th Edition, **2024 rules**, using the free official **System Reference Document 5.2.1** (see §6). |
| Seating | Players sit **all around** the Main Screen, so its layout must read from every side (see §3.1). |
| Map look | Inspired by **Watabou's** procedural generators (watabou.github.io), with a hex grid on top (see §10a). |
| Grid | **Always hexagons**, fixed grid, on every map. |
| World | Open and procedurally generated: regions → villages/locations → interiors (houses, caves, dungeons) generated when entered. Everything can be edited by the DM. |
| Tokens | Generated by the app. Can be moved from a player's own device **or** on the Main Screen. Real miniatures can be placed on top. |
| Physical scale | Each screen is **calibrated** before play so a hex has a known real-world size (for miniatures). |
| Tokens show info | Movement range and attack/spell range highlighted on the hex grid. |
| Combat | Like the tabletop game: initiative, turns, actions, bonus actions, reactions, movement. |
| Saving | Critical. The full game state is saved continuously and restored exactly. |

## 3. The three screens

### 3.1 Main Screen (shared table display)
- Creates a game session and shows the **room code + QR code**.
- Shows the current map: hex grid, terrain, buildings, tokens, fog of war.
- Shows only what the DM has revealed, never DM-only notes or hidden monsters.
- Shows the initiative order, whose turn it is, public dice rolls, and big moments (critical hits, level-ups).
- Touch: tokens can be dragged here (if the DM allows it). Pinch to zoom and pan is **locked during play** so miniatures stay lined up; only the DM can move the view.
- Runs a **scale calibration** (see §5).

**Readable from every side** (players sit all around the table):
- Each player picks their **seat** (the edge or corner of the screen nearest them) when joining.
- Personal info (e.g. "Your turn, Mira!", that player's dice result) appears at **their edge, rotated to face them**.
- Shared info (initiative order, round number) is shown along **all four edges** or as a central ring, never as text that is only upright for one side.
- Token labels are short and rotate toward the token owner's seat (or are hidden; names show on phones instead).
- The map itself has no "up": a compass rose shows north.

### 3.2 Player device (phone/tablet, one per player)
- Join with the room code or QR code, then pick or create a character.
- Character sheet: ability scores, HP, AC, conditions, spells and slots, features, inventory, gold.
- Action menu: Move, Attack, Cast a Spell, Dash, Dodge, Help, Hide, Use an Object, and so on.
- A mini-map to move their own token; reachable hexes are highlighted.
- Dice roller (public rolls go to the Main Screen; secret rolls only to the DM if the DM asks).
- Private messages and handouts from the DM.

### 3.3 DM device (tablet/laptop)
- Sees **everything**: the full map, hidden things, monster stats, notes.
- Generates, regenerates or edits maps, locations and NPCs.
- Places, hides and reveals tokens, monsters, traps and treasure; controls the fog of war.
- Runs combat: starts and ends encounters, controls monsters, approves or undoes actions.
- Decides what the Main Screen shows (which map, where the camera points, which areas are revealed).
- Can override any rule or number (the DM is always right).
- Save, load and manage campaigns.

## 4. The world: procedural, layered, editable

The world is a set of **maps**, each on a hex grid, linked like doors:

```
World / Region map (each hex ≈ 1 mile, overland travel)
 └─ Location map: e.g. "Village of Brindlemoor" (each hex = 5 ft)
     ├─ Interior: "The Gilded Tankard" tavern (each hex = 5 ft)
     ├─ Interior: "Old Miller's House"
     └─ Location: "Cave north of the village"
         └─ Deeper cave level...
```

- **Generated on demand:** a map is only generated the first time someone enters it, so the world can be as big as the players' curiosity.
- **Seeded generation:** each map has a *seed* (a number). The same seed always gives the same map, which keeps saves small and makes "regenerate" possible.
- **DM edits are stored on top** of the generated map, so changes are never lost.
- **Generated content per location:** name, layout, terrain and buildings, NPCs (name, role, personality, short description), loot and encounters (from the SRD monster and item lists, scaled to party level).
- **The DM can always:** regenerate, edit hexes by hand, rename things, add or remove NPCs and monsters, or lock a map so it never changes.

### Map scale
- Tactical maps (towns, interiors, dungeons): **1 hex = 5 feet**, the standard 5e combat scale.
- Overland/region maps: 1 hex = a travel distance (e.g. 1 mile). Combat never happens on these; entering an encounter opens a tactical map.

## 5. Physical scale and miniatures

Screens differ in size and pixel density, so the app can't know how large a hex looks on the table without help.

**Calibration (before the game starts, on the Main Screen):**
1. The screen shows a rectangle the size of a **credit/bank card** (85.6 × 54 mm, the same on every card). The user drags until the rectangle matches a real card held against the screen. A ruler-based option is also available.
2. The app now knows pixels-per-millimetre for that screen and saves it on that device.
3. Hexes are drawn at the chosen real-world size. The default is **1 inch (25.4 mm) across**, which fits standard 25–28 mm miniature bases. The size can be changed.
4. A test pattern is shown so players can put a miniature on a hex and confirm.

**Consequences:**
- During play the Main Screen does not zoom (scale must stay true). The DM pans the view; areas that don't fit are reached by panning.
- Token sizes follow 5e creature sizes: Tiny/Small/Medium = 1 hex, Large = a 3-hex or 7-hex cluster, Huge and Gargantuan larger clusters (exact footprints to be decided).
- Phones and the DM device don't need calibration; they zoom freely.

## 6. Rules: 5th Edition, legally

**Important:** the full Player's Handbook, Monster Manual and Dungeon Master's Guide are copyrighted and can't be copied into the game. However, Wizards of the Coast has released the core rules for free use:

- **SRD 5.2.1** (the 2024 rules), licensed **CC-BY-4.0**: free to use, change and even sell, as long as we include the attribution text. Download: <https://www.dndbeyond.com/srd>
- **SRD 5.1** (the 2014 rules), also CC-BY-4.0.

The SRD covers the core mechanics, combat, conditions, spells, many monsters, equipment and magic items, plus a subset of classes, subclasses, backgrounds and species. Content not in the SRD (most subclasses, named settings and characters, some iconic monsters) can't be bundled, but **the DM can add their own homebrew** content in the app.

**Data source:** the open-source project **5e-database** (<https://github.com/5e-bits/5e-database>) already has the SRD in structured JSON, for both the 2014 and 2024 rules: classes, species, backgrounds, feats, spells, monsters, equipment, magic items, conditions, and more. We'll import this instead of typing the rules in by hand.

**Decided:** use the **2024 rules (SRD 5.2.1)**, the `src/2024/en` data in 5e-database.

**Rules automation:** the app calculates the routine parts (modifiers, attack rolls vs AC, damage, saving throws, spell slots, movement and range, conditions, initiative), but the **DM can override anything**.

## 7. Tokens, movement and ranges

- Every character, NPC and monster gets a **generated token**: a coloured hex disc with an icon or portrait and a short label. Player tokens have the player's colour.
- **Moving:** a player moves their own token from their phone **or** by dragging it on the Main Screen. The DM can move anything. The DM can choose whether moves need approval.
- **Movement range:** when it's your turn, reachable hexes are highlighted, including difficult terrain (counts double) and remaining movement.
- **Attack/spell range:** choosing an attack or spell highlights hexes in range (normal and long range in different shades) and shows areas of effect (cone, sphere, line, cube) on the hex grid.
- **Miniatures:** the token stays visible under a real miniature (its outline and a ring in the player's colour), so it's clear which figure is where.

## 8. Combat (5e turn structure)

1. The DM starts an encounter and picks the participants.
2. **Initiative** is rolled (automatically or manually) and the order is shown on the Main Screen.
3. On each turn: **move** (up to Speed, can be split), one **Action**, one **Bonus Action** if available, one **Reaction** per round (e.g. opportunity attacks, prompted automatically).
4. Attacks: roll d20 + modifiers vs AC → damage roll → HP updated → conditions applied.
5. Death saves, concentration checks, conditions and durations are tracked automatically.
6. The DM controls monsters, can undo, and ends the encounter.

## 9. Saving: exact restore

- **Everything lives on the server** in a database: maps (seeds + DM edits), tokens and positions, characters, HP, spell slots, conditions, inventory, initiative and the current turn, fog of war, NPCs, DM notes, and what the Main Screen is showing.
- **Autosave after every change.** No "save" button is needed (a manual named save or snapshot is also available).
- **Event log:** every action is recorded. This allows undo and a session recap ("last time on...").
- **Resume:** the DM opens the campaign and the Main Screen and all players reconnect to exactly the same situation, even mid-combat on the same turn.
- **Reconnects:** if a phone locks or loses Wi-Fi, it rejoins automatically.

## 10. Technical plan (proposed)

| Part | Choice | Why |
|---|---|---|
| Language | **TypeScript** everywhere | One language for every screen and the server; it catches mistakes early. |
| Screens (frontend) | **React** for menus and sheets, **PixiJS** (WebGL) for drawing the hex map | Fast, smooth rendering of large maps and many tokens on tablets. |
| Real-time connection | **WebSockets** (e.g. Socket.IO) | All screens update instantly. |
| Server (backend) | **Node.js** | Holds the authoritative game state and applies the rules, so devices can't get out of sync. |
| Database | **PostgreSQL** (SQLite for local development) | Reliable saving. |
| Hex maths | Axial/cube coordinates (the well-known approach from Red Blob Games) | Simple distance, range, line-of-sight and area calculations on hexes. |
| Procedural generation | Seeded random generator + noise for terrain, templates for buildings, name generators | Repeatable, editable maps. |
| Hosting | A cloud host (e.g. Fly.io, Render or Railway) | Cheap or free to start. |

**Account/login:** keep it simple at first. The DM has an account (to own campaigns); players join with a room code and claim their character.

## 10a. Visual style

Inspired by **Watabou's generators** (Medieval Fantasy City Generator, village and dungeon generators):
- Clean, **ink-on-paper** look: crisp dark outlines, flat muted colours, a light parchment or off-white background.
- Buildings drawn as simple filled blocks with thin outlines; roads, rivers, walls and fields as soft shapes; trees as small round clusters.
- Dungeons and caves in a "one-page dungeon" style: white rooms on a dark or hatched background.
- Minimal labels in a fantasy-but-readable font.

**Changes for our game:**
- A **hex grid is drawn over every map** (thin, semi-transparent lines so the art stays readable), and generation is **hex-aware**: walls, doors and building edges follow hex edges, so every hex is clearly floor, wall, door, water, etc. That's needed for movement and range rules.
- The colours must stay readable under miniatures and on a bright tablet; highlights (movement, range, AoE) use strong, colour-blind-safe overlays.
- A light and dark theme for different table lighting.

**How we use Watabou's work:** we **write our own generators** in a similar style; we don't copy or embed Watabou's site. Watabou's city generator source code (TownGeneratorOS) is public under the **GPL-3.0** licence. We can study its ideas freely, but copying its code would require this project to also be GPL-3.0. That's fine for a personal project, so we'll decide case by case. Watabou's other generators are not open-source, so we only take visual inspiration from them.

## 11. Open questions

Decided in v0.2: 2024 rules ✔ · name "dnd" for now ✔ · players sit all around the screen ✔ · Watabou-inspired style ✔

Still open:
1. **Large creatures on hexes:** what footprint shapes to use for Large/Huge/Gargantuan?
2. **Line of sight / fog of war:** reveal automatically based on what tokens can see, or only by hand by the DM? Proposed: automatic, with the DM able to override.
3. **Character creation:** on the phone before the first session, or can the DM pre-make characters?

## 12. Build order (milestones)

1. **Connect the screens:** Main Screen creates a room, phones and the DM join by code or QR, everyone sees each other connected.
2. **Hex map + calibration:** draw a hex grid at true physical size on the Main Screen; tokens that can be dragged and stay in sync on all devices.
3. **Saving:** state stored on the server; close everything, reopen, same situation.
4. **Rules data:** import the SRD (5e-database); character creation and character sheet on the phone.
5. **Movement and range highlighting** on the hex grid.
6. **Combat:** initiative, turns, attacks, damage, conditions.
7. **Procedural generation:** region map → village with name and NPCs → enterable buildings and caves generated on demand.
8. **DM tools:** map editor, fog of war, monster placement, overrides.
9. Polish: art, sounds, recaps, homebrew content.
